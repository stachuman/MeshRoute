### 2026-08-14 review corrections to B196-B198 — authoritative over the historical wording in those rows

The three rows above were recorded before the source audit and contain statements that must not be used as current
facts. They remain visible as history; the corrections here supersede them.

- **B196:** the 41-second clustering strongly suggests a repeatable trigger, but it does **not** establish the trigger
  class and does not exclude memory corruption. Deterministic corruption tied to a counter, allocation pattern, or
  repeated event can cluster at a fixed uptime too. The timing alignments are instrumentation choices, not evidence
  of causation: nine hours is 36 default 15-minute static-beacon periods, 108 default 5-minute team-mobile beacon
  periods, and nine configured one-hour duty-window lengths. The duty window is a rolling horizon, not by itself an
  hourly scheduled callback. The supplied “18 × 30-minute mobile reclaim” alignment is **not a fact about the current
  tree**: `protocol::mobile_reclaim_ms` is 600000 (10 minutes), so current code has 54 such periods in nine hours.
  The exact previous revision must be checked before using reclaim cadence as a marker.

  Before another run, establish whether `crashtest fault` was used during any of boots 38-44. Preserve the exact
  firmware revision and its matching `firmware.elf`. Run a minimum 10-hour soak with two simultaneous, otherwise
  identical arms and read-only serial capture: one headless arm receives no console byte after boot; the awake-host
  control receives one byte during the 30-second grace period. Keep configuration and RF topology identical. Capture
  the complete IDF panic output, then decode its backtrace against the retained ELF. Only that evidence can justify a
  fix. One clean 10-hour run on current firmware would show that the old trigger is not trivially reproducible; it
  would not prove the defect gone. The earlier “one capture should suffice” claim is withdrawn.

- **B197:** the panel going dark is **not** evidence that `MR_BOOT_GRACE_MS` expired. Its independent authority is
  `kBlankMs = 15000` in `src/firmware_ui_model.h`; boot grace is 30000 ms in `src/fw_main.cpp`. The statement that no
  input can bring a sleeping node back is also withdrawn. There is no reliable edge-triggered user wake today, but a
  sufficiently long active-low press can be sampled during a periodic timer wake, exactly as the metal reproduction
  observed. UART input alone remains unable to wake the node. The supported recovery designed for the fix is button
  wake, a fresh monitor/DTR reset, or a console byte received during boot grace.

- **B198:** board-private `s_painting` is not the sleep-policy authority and must not escape `board_ui.cpp`.
  `FrameGate::frame_open()` already exists and is the logical authority; implementation adds only the missing
  read-only `InputFsm::active()`. Keep the page-buffer design and one-page-per-service-pass contract. The combined
  B197/B198 design is
  `docs/superpowers/specs/2026-08-14-b197-b198-ui-sleep-wake-design.md`; it is design-only and claims no approval.
