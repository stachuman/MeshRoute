## K3 (spec :891-917, quote-level)
- ★★★ **THE ORDERING RULING (F-10):** `mr_ui_on_push(pu)` is the FIRST statement in the drain loop
  (`src/fw_main.cpp:1310` — verify), so for `team_key_received` a **config-service persistence function runs
  FIRST, and only a `saved` return forwards the push** to `mr_ui_on_push`. On failure the UI ⛔ never shows
  `TEAM KEY RECEIVED`; the failure is reported explicitly as RAM-only / lost-on-reboot.
- ★★ **THE FOUR HANDLING-TIME RE-CHECKS** (a push drains after RX; membership can change between): at handling
  time — `pu.team_id != 0` · `pu.team_id == g_node.config().team_id` · the live key is present · the loaded
  blob belongs to the same team. ⛔ Any one failing ⇒ nothing written, the UI not told a key was adopted.
- Order: **persist {team_id, key} FIRST → mark active → then the note (K4).** Files:
  `src/firmware_team_keyring.h` (the decision — pure) · `src/firmware_config.cpp` (the forward) ·
  `src/fw_main.cpp` (**the ONE structural change**: the routing; ⚠ U3 — fw_main gains a call, ⛔ not a decision).
- ⚠ **`§notify-every-save`, measured not omitted:** a grant receipt is not user-initiated and assigns none of
  the four covered `/mrcfg` fields ⇒ it stays SILENT, **recorded beside the existing exemption list**
  (`src/firmware_config.cpp:694-706`) so no future reader treats it as an oversight.
- **Pins:** (1) successful persist ⇒ push forwarded. (2) FAILED persist ⇒ ⛔ push not forwarded, failure
  surfaced. (3) each of the four re-checks fails the write on its own — four cases, four mutations.
  (4) a re-grant replaces that team's record atomically and idempotently. (5) a different team's grant is
  refused upstream (`team_mismatch`, `lib/core/node.cpp:258` — verify) and writes nothing. (6) identical
  material ⇒ **zero writes** (counted — the K1 coalescing discipline).
- **Mutations (`teamkeyring`, `config`):** the push forwarded BEFORE the persist (F-10 restored — the headline)
  · forwarded on a failed persist · each of the four re-checks dropped · the active mark written before the
  durable save returns.
- ⛔⛔ **SECRET HYGIENE unchanged (K1's):** no key byte printed/echoed/logged/in errors; wipes via the existing
  discipline; the keyring's own refusal funnels reused, never re-spelled (U1).
