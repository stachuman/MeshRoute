## The ruled mechanisms (quote-level, spec :705-736)
- ★★ **TWO AUTHORITIES (F-11):** (a) authoritative hashes at opening — survives a team-local-id change; (b) a
  bitset of team-local ids present at opening — suppresses an already-present member whose hash arrives later.
  **NEW ⟺ neither the hash nor the current id was in the opening snapshot.** The **double-change** case prompts
  and is documented in-source as a **SAFE FALSE PROMPT** — ⛔ not engineered away, not a bug.
- ★ Candidates built through `team_key_of_id` at the **authoritative** floor (F-7, C2): a route-only member is
  ⛔ not listed as grantable, while its id is still in authority (b).
- ★★ The candidate row (F-15 rules 2-3, S-35): `%c%-6.6s T%-3u %6s` = marker · name (6, **blank until known**) ·
  team-local id · member fingerprint (6); width proof `1+6+1+4+1+6 = 19`. ★ **The fingerprint NEVER leaves the
  row** — a cached name fills the separate blank column, ⛔ never substitutes. ★ Name source =
  `Node::peer_name_find` and NOTHING else — ⛔ never `label_from_hash`/`label_for_team_id` (their `0x%08lx`
  fallback = a third spelling of the hash). Clamp `%-6.6s`, matching the TEAM row's, one truncation per name.
- ★ The window refreshes **locally** while active (F-14): re-reads `rt_team_at`/`team_key_of_id`, both `const` —
  ⛔ no scan and no refresh traffic. B249's one triggered-announcement request belongs only to the fresh open.
  **Opening a confirmation FREEZES the selected hash/id.**
- ★ A separate deadline: `_invite_until_ms` + `window_active(now)` beside `hold_active(now)`, wrap-safe the same
  way (U3) — ⛔ **must not write `_last_input_ms`**. ✅ OQ-3: **5 minutes**, does NOT hold the panel lit, the
  window survives the blank, an unfinished confirmation does not.
- ★ The handled set (F-13): `REJECT` **and** a queued grant add the candidate's **hash**; ⛔ no core/radio/
  membership/key/NV state; **discarded when the window closes**.

## Pins (spec :737-753, verbatim — every one a case)
(1) the window expires by itself; expiry ⛔ grants/revokes/rewrites nothing (P-11: across open→expire→re-open,
`team_channel_key_present()`, `rt_team_count()` and the member set byte-identical). (2) present-at-snapshot ⇒
⛔ never a candidate. (3) appearing after ⇒ a candidate exactly once. (4) ★ re-DAD'd (same hash, new id) ⇒ ⛔ not
a candidate. (5) ★ route-only hash turning authoritative mid-window ⇒ ⛔ not a candidate. (6) ★ the double-change
case DOES prompt — driven directly, measured not asserted. (7) the word is `NEW MEMBER`; ⛔ `KEYLESS` nowhere.
(8) ★ a REJECTed candidate does not return on the next refresh AND returns after close+re-open. (9) the screen
shows the team's own fingerprint, ⛔ no label. (10) ★ fresh open: snapshot first, then exactly one existing triggered
team-announcement request; holding/refreshing/redrawing/waking/confirmation-return/closing: zero additional requests.
(11) window closed ⇒ a new member changes ⛔ no screen, cursor or note (P-12). (12) the row hidden on a teamless
node and on `gateway_heltec`. (13) the window survives blank/wake; an unfinished confirmation does not.
(14) no cached name ⇒ blank name column + member fingerprint; ⛔ the fingerprint column never empty. (15) a
cached name ⇒ name clamped to 6, fingerprint unchanged. (16) row identity = `key_hash32`; two candidates with
the same cached name are two rows, selecting independently. (17) every confirmation opened from the list carries
the **full `0x%08lX` hash**, ⛔ even when a name is shown.
