## The ruled facts (spec :943-949, verbatim)
- When **N3's join targets a team whose key is RETAINED in the keyring**, the flow offers **`SAVED KEY FOUND`**
  with **`BACK` selected** and an explicit **`USE SAVED KEY`**.
- ⛔ **Nothing is installed by mere knowledge of the public team id (P-2b)** — that is the whole reason this is
  a SCREEN and not a rule. `BACK` ⇒ **installs nothing and changes no key state** (⛔ corrected 2026-08-25,
  final QG: this read "the node stays keyless" — after an A→B membership change BACK correctly leaves B's key
  untouched), the record stays retained and untouched — exactly
  the pre-K5 behaviour.
- ⛔ **`FORGET KEY` is NOT in this spec** (a ruled future verb — do not add it, do not stub it).

## Design constraints (from the landed tree — derive, verify, REPORT prominently)
- **The activation is a REUSE, not a new path (U1/U2):** `USE SAVED KEY` performs what the tree already knows
  how to do — install the retained record's key live + commit the `/mrcfg` active binding (K2's
  `commit_active` side; the K1 five-term predicate then makes it boot-durable). ⛔ ONE existing activation
  path, cited; if none is cleanly callable, STOP and report — never fork a second install sequence.
- **Where the screen sits in the join flow** is yours to derive from the landed N3 shape and REPORT as a
  design decision (the N6 `GRANT PARKED` precedent — reported, not assumed). The constraint set: the join
  itself must still succeed/fail exactly as N3 landed it (membership is never gated on the key decision);
  the offer appears only when the join's target team has a retained record (the keyring lookup is a read,
  through an existing accessor); BACK is the default and costs the operator nothing; the screen honours the
  UI-17 navigation contract and OQ-3's rule that an unfinished confirmation does not survive blanking.
- **The result wording after `USE SAVED KEY`:** ⛔ **SUPERSEDED 2026-08-25 (kept visible):** this bullet read
  "the §8 inventory rules NO result lexeme … STOP and report the candidate for ruling". The process it demanded
  RAN: success reuses **S-26 `TEAM KEY ACTIVE`** (true — live AND durable), and the failure candidate was
  reported and **owner-ruled as §8 S-39 `KEY NOT INSTALLED`** — the act's outcome, never the node's key
  inventory, true on every refusing arm.
- **Secret hygiene (K1's, unchanged):** no key byte printed/echoed/logged; a failed activation fails LOUDLY —
  never half-installed. ⛔ **CORRECTED 2026-08-25 (QG round 2 + owner): this line read "the keyring's refusal
  funnel reused; … leaves the node keyless" — BOTH halves were withdrawn by the stale-membership fix.** The
  funnel's clearing is for verbs where the live key is the SUSPECT (boot restore / receive); here it is
  INNOCENT (it may be another team's), so `use_saved` refuses SURGICALLY — clears nothing except the one
  `binding_failed` undo of its own install — and a refused stale activation leaves whatever key was live
  exactly as it found it.
- **P-2b's mutation is the headline:** the key installed on reaching the screen (or on the JOIN alone) without
  the explicit `USE SAVED KEY` double — RED at match count 1. Its sibling: the offer appearing for a team with
  NO retained record.

## Pins (minimum set — extend where the design demands)
(1) A nearby join of a retained-key team ⇒ the offer, `BACK` selected. (2) `BACK` **installs nothing and
changes no key state** — record untouched, byte-identical blob (the K3 idiom: counted, zero writes). ⛔
**CORRECTED 2026-08-25 (final QG): this pin read "`BACK` ⇒ keyless" — an OVERSTATEMENT once the surgical-refusal
fix landed: after an A→B membership change, `BACK` correctly leaves B's key untouched. The invariant is "BACK
changes no key state", and the same wording governs every refusal — refusals install nothing and preserve
unrelated existing key state; only `binding_failed` undoes this operation's own adoption.** (3) `double` on
`USE SAVED KEY` ⇒ key live +
binding active + boot-durable (the five-term predicate satisfied — drive the restore path against the written
state). (4) A join of a team with NO record ⇒ ⛔ no offer, the landed N3 flow byte-for-byte. (5) A FAILED
activation ⇒ loud, **installs nothing, preserves unrelated existing key state** (⛔ corrected 2026-08-25, final
QG: this read "keyless" — only `binding_failed` undoes this operation's OWN adoption; any other team's live key
is untouched), record intact. (6) ⛔ Nothing transmitted by the offer, either choice, or the
activation (zero-TX counted). (7) The screen carries the team fingerprint via the ONE helper; ⛔ no
name-shaped value as identity (S-36). (8) Blank/wake: the unfinished offer does not survive; the landed
retention rules for everything else do. (9) The N3 keyless-non-anticipation case FLIPS deliberately: the old
"stays keyless even with a retained record" pin is REPLACED by the offer — update that case with the
correction idiom (withdrawn expectation kept visible), ⛔ never delete it.
- Mutations: the P-2b pair above · BACK performing the install · the activation forking a second install path
