## TPR-1 — MAJOR: comparison validates a self-declared subset, not the required matrix

**Anchors:** brief **B7–B8, :357–375**, B10 comparison controls :402–403; `transcript.py::derive_matrix` :192–231 and the driver's `MR0C_MATRIX` loop at `transcript_main.cpp::main`.

B7 checks a freshly executed ledger against the known matrix. B8 instead says an imported ledger validates against **its own** `lines=` count, unique ordered IDs, one SER/BLE pair per LINE, and END last. It never requires the declared profile's complete expected matrix. Its explicit exit-0 condition is identical rows.

Two identical empty ledgers with `lines=0`, a correct five-macro profile and END therefore satisfy the literal B8 rules. So do two identical one-row ledgers with a rewritten `lines=1`. These are supplied as **specification counterexamples** beside this report; they were not run through a nonexistent implementation of `--compare`. A test that simply removes a row without updating its count does not catch this omission.

There is also an underspecified record boundary: the B7/B8 lists require SER/BLE prefixes, without saying that a missing sink or fingerprint field is malformed. B7 checks the LINE's ID and length, but not that its escaped command bytes match the corresponding matrix input. A repeated truncated or corrupted capture must not become a valid regression baseline just because its two copies agree.

**Required correction:** make the run and comparison paths use one explicit validity contract. For this package, derive the expected ordered `(ID, command bytes, length)` matrix from the declared supported profile and current inventory without compiling. Require the complete set, exactly one matching compiled-profile line, internally consistent counts, full record grammar/fields, and the expected terminal record. Then compare only validated records. Keep source hash, path, label and adapter identity as reported provenance, as intended.

If historical comparisons need another expected matrix later, that must be an explicit input/contract rather than implicit trust in the artifact's own count. The current historical use already projects both executions against the same inventory; this correction does not require a second firmware build or broaden the product fence.

Add no-build regressions for both empty ledgers; both truncated ledgers with adjusted counts; an unknown/missing row with adjusted count; wrong command bytes at unchanged ID/length; and a malformed or incomplete SER/BLE record. Each refuses with exit 2. Existing valid equal/different comparisons still give 0/1. Include a control that bypasses the expected-matrix check so the completeness regression demonstrably fails.

## TPR-2 — MAJOR: blanket control rule contradicts B-C6's required build refusal

**Anchors:** brief **B10.4 :395–405** and **§4.3 :556–558**.

B10 says every control must fail its intended assertion and never pass by a build failure. The STOP list repeats the blanket prohibition. But **B-C6** deliberately removes `device_ble.h` and explicitly requires a build refusal with exit 2 and no ledger. B-C3 and B-C5 likewise prove named tool refusals rather than assertion failures in a successfully executed comparison. A coder following the generic rule would have to STOP on a required successful B-C6 result.

**Required correction:** classify controls by their actual contract and use that classification in the gate/STOP list:

- B-C1/B-C2: the altered driver must build and run normally; the intended record assertions/comparison detect the changed behavior. A build failure or crash is unusable evidence.
- B-C3: a built driver with the deliberately incomplete profile must produce the named profile refusal.
- B-C4: valid-record differences give 1; malformed/incomplete ledgers give the named validation refusal, 2.
- B-C5: the compiled driver must reach its explicit unrepresentable-row refusal; verify the reason and tool exit 2, not an arbitrary crash or compiler failure.
- B-C6: the deliberate missing declaration must produce the identified compiler diagnostic and the tool's build refusal, exit 2, with no valid ledger. This is the narrowly allowed compile-refusal control.

Do not relax the general rule to accepting any nonzero exit. Keep build failures distinguished from signal deaths, missing tools, unrelated diagnostics and vacuous source edits. Part A's deliberate decoder exception remains a failing regression outcome under its stated A9 rule, never an assertion verdict credited to a mutant.

## TPR-3 — MAJOR: transfer-integrity failure behavior has no required fault proof

**Anchors:** brief **A5 :222–230**, **A9.3–A9.5 :267–294**, final gate §4.1 steps 3–5. Existing source: `orchestrate` result merge :12614 onward and exit precedence :12755–12763.

A5 adds real decisions: independently recompute a worker's length/hash, reject mismatches, verify the parent's persisted copy, classify failed writes as integrity failures, and preserve agreed-abort precedence. A9's end-to-end runs exercise correctly transferred UNUSABLE records (exit 1) and correctly transferred baseline refusals (exit 2). Its write-deletion and bounded-retention controls prove missing evidence is noticed by the **test**. They do not require the **runner itself** to detect corrupt worker metadata or report an actual retention I/O failure through its prescribed integrity path.

An implementation could omit the declared-versus-observed hash check, or leave an unhandled exception on a failed parent write, and still satisfy the named successful-transfer cases and controls. These paths govern the evidence whose preservation is the package's purpose.

**Required correction:** extend the same temporary-tree/fake-pio regression, using labelled synthetic faults, with:

1. A corrupted worker stream or declared length/hash. Require a named integrity failure, no valid battery result, and exit 9 when workers otherwise return verdict exits 0/1. Demonstrate an exact control bypassing the relevant comparison makes this regression fail.
2. An actual failed parent retention write, e.g. a deliberately obstructed output path. Require the named integrity diagnostic, no uncaught traceback and exit 9 for the normal-worker case. State what evidence remains available when persistence itself fails; do not claim successful retention.
3. At least the all-workers-baseline-refused case combined with a retention failure: preserve the specified unanimous exit **2**, but still print the independent integrity failure. This proves the explicitly retained precedence rather than changing it incidentally.

The synthetic mechanism belongs only in the test fixture or an exact one-site control copy. No product hook, new tool file or full mutation union is required. Keep source restoration and cleanup assertions on these paths. Expand A9's “exit 1, never 9” wording to apply to its ordinary mixed-verdict scenario, not these intended integrity failures.
