## 3. Both rule-7 acceptances, and every independent refusal

### 3.1 The two production transports, and why there are two

`for_static_rts` (`node_mac_rx.cpp`) admits a unicast RTS at a MOBILE only when `addr_len == 1`, which exactly
two production senders set. S4's cases therefore run on both, and neither is a convenience:

- **A — the hosted direct last mile.** `send_by_hash` at the mobile's OWN home; carries **no `DST_HASH`**; its
  bytes are whatever the home's correlation produced. This is the arm §B278 S3 originates on.
- **B — the home last-mile forward.** A `DST_HASH`-addressed DATA reaching the mobile's CURRENT home, which
  forwards it verbatim to the local id (the §CUSTODY-G/4b role). The origin stays the ORIGINATING home, which
  IS §8.2 rule 7's re-homed shape: `pa.origin == failed_origin == H1` while the last mile happens at H2.

Three contexts neither transport can install — a CRYPTED carrier, a TEAM-plane arrival, and a FOREIGN
`DST_HASH` (which `do_post_ack` redirects through `l2c_handle_misdelivery` long before the receiver) — are
driven through the `MESHROUTE_NATIVE` seam off a COPY of the LIVE `PostAck` the production MAC really left
behind, with EXACTLY ONE field changed. That is §CUSTODY-G's own rule, applied unchanged.

## 4. The store/Push order and §8.3's two mappings

Observable order inside `Node::custody_failure_receive`, top to bottom:

```text
frame terms -> parse prefix (ONE call) -> branch on bit 6 -> read tail (ONE call, translated only)
   -> the common receiver terms -> the mode's context -> derive out_origin / out_ctr / out_layer ONCE
   -> _inbox.record_custody_failure(out_origin, out_ctr, out_layer, rec_bytes, rec_len, now) -> seq
   -> enqueue_push(pu) carrying that seq        -> MR_EMIT("custody_failure_rx", …)
   -> if (translated) return;                   -> [direct only] S3's lookup / origination
```

| | direct | translated |
| --- | --- | --- |
| record origin / Push origin | `pa.origin` | `tail.original_reporter` |
| record msg_id / Push ctr | `rec.failed_ctr` (ctrH) | `tail.mobile_ctr` (ctrM) |
| Push dst | `rec.failed_dst` | `rec.failed_dst` |
| layer | `active_layer_id()` | `rec.reporter_layer` |
| body / body_len | `record_len` bytes | `record_len` bytes, incl. every accepted future byte |
| `Push::reason` | `none` | `none` |
| `seq` | the store's return value | the store's return value |

⛔ **The three values are derived ONCE and read by all three surfaces** (store, Push, telemetry), so a report's
public identity cannot differ between the record the app pulls, the push it receives live and the event the
corpus counts (U2). Measured, not argued:

- **§B278-S4/2** — `push_origin == 2` (the ORIGINAL reporter, ⛔ **not** the translating home, whose id is 1),
  `push_ctr == 0x0777` (ctrM, ⛔ not ctrH `0x0BEE`), `push_dst == 9`, `push_layer == 2`,
  `push_body == s3_expected_body()` (the whole 32 bytes), and the store agrees field for field with
  `stored_seq == push_seq` and `push_seq != 0`. **Store BEFORE Push, made observable.**
- **the factual telemetry**, pinned by NAME, FIELD ORDER and integer type, on a fixture where the two
  identities are DISTINGUISHABLE on purpose: `custody_failure_rx{reporter=2, dst=9, ctr=0x0777, seq}` — the
  carrier's origin is 1 and ctrH is `0x0BEE`, so an event reporting the carrier would be visible rather than
  plausible.
- **§B278-S4/9 — the accepted FUTURE tail.** A `record_len = 40` translated record (the 32 defined bytes plus
  eight this build cannot interpret) is stored and pushed **whole**: `stored_len == 40`,
  `stored_body == body`, `push_body == body`, identity still the tail's. And presentation still reads only the
  KNOWN 32-byte prefix: the JSON of the 40-byte record and of its 32-byte prefix are **identical strings**.
- **§B278-S4/9b — storage disabled.** One live Push still fires with `seq == 0` and `stored == 0`, identity
  and body unchanged.
- **§B278-S4/10 — the `return` is the contract.** On a mobile that DOES hold a live eligible delegated row (an
  unreachable state made measurable through the ring's own production seam), all four S3 events are 0, the row
  is untouched (`eligible` 1, `forwarded` 0), `tx_n == 0`, `parked_n == 0`, zero RTS. The DIRECT control in the

  empty ring.
- **§B278-S4/14 — non-recursion.** Consuming one produces exactly ONE push, `other_pushes == 0` (no
  `send_aired`/`send_failed`/`msg_recv`), `custody_notice_tx == 0`, `e2e_ack_tx == 0`, `delivered == 0`.
