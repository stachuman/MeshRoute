### ★ Finding F1 — the advertised wait is not enforced, and neither is the 60 s cap, on this arm

§4.2 of the spec states: *"Above 2 s the sender requeues the exact bytes with no added backoff **until the existing
60 s send-lifetime cap**."* The first half is right; **the second half is not what the code does.**

- `become_free` picks the next queue item purely on `next_attempt_ms <= now` (`node_mac.cpp:922-932`), and the
  BUSY_RX long-busy arm sets `next_attempt_ms = 0` (`node_mac_rx.cpp:2587`) ⇒ **immediately ready**.
- The 60 s bound lives in `cascade_terminal_cause` (`node_cascade.cpp:69-76`), reached only from
  `try_cascade_requeue`. The BUSY_RX arm **never calls it** — measured: `cascade_requeue` count is **0** across
  all 32 attempts.
- `requeue_count` is **not incremented** (`node_mac_rx.cpp:2585`), so `cascade_requeue_max` can never trip either,
  and `effective_rts_max_retries(requeue_count)` restores the **full** RTS retry budget on every attempt
  (`node_mac.cpp:1074`).
- The `_blind_until[next]` mark the arm does set (`node_mac_rx.cpp:2574-2577`) is read **only** by
  `next_hop_selectable` (`node_cascade.cpp:518`) — the *cascade's alternate-hop* filter. The primary drain never

property of the driver; only the *absence of a bound* is a property of the code.

### Multi-sender synchronization

**What is measured:** the refusal is per-arrival and stateless, so a second, unrelated hosted mobile arriving in

**What is NOT measured, and is not extrapolated:** whether their retries collide *on air*. There is no channel to
